# 보유 장비로 진행할 실제 데이터·실차 구현 요구사항

작성일: 2026-10-22. 사용자 피드백을 반영한 **후속 구현 요청**이다.
이 문서의 작업은 아직 완료되지 않았다. 기존 시뮬레이션 구현과 검증 범위는 [검증 기록](validation.md)을 따른다.

## 목표와 자원 범위

Ubuntu·RTX 5070 노트북·Isaac Sim 5.1에서 합성 데이터를 생성하고 학습한다.
실제 추론·모터 제어는 보유한 Raspberry Pi 5 차량에서 수행한다. 보유 트랙과 차량 카메라로 실제 데이터를 수집한다.
RTX의 실제 VRAM, Pi OS·메모리·냉각 상태와 엔코더 장착 여부는 기기에서 확인한다.

추가 하드웨어 구매·유료 클라우드·상시 원격 추론을 기본 전제로 삼지 않는다.
Jetson/TensorRT, Mega·플릿 운영, DRIVE Sim 연동은 이번 구현 범위에 넣지 않는다.
산업 사례는 보고서 배경 자료로 활용한다. 무작위화·검출·미션 등 기존 코드를 기반으로 아래 네 항목을 순서대로 구현한다.

| 우선순위 | 후속 구현 | 완료 근거 |
|---|---|---|
| 1 | 실제 영상·조작값 수집 및 세션별 분리 | 동기화 기록, 고정 분할 manifest, 세션/원본 중복 검사, 클래스 분포 |
| 2 | 합성 가중치에서 실제 데이터 미세조정 | 체크포인트·학습률 옵션, validation 기반 선택, 별도 최종 test 평가 |
| 3 | 실제 카메라 추론과 모터 제어 분리 | 최신 프레임 처리, 별도 제어 주기, 만료·추론 실패 시 정지 검증 |
| 4 | Pi 지연·주행 성능 측정 | 단계별/전체 지연 분포, 제어 주기 지연, 완주·미션 완료/실패 기록 |

## 1. 실제 데이터 수집과 분할

실제 차량 카메라의 화각·높이·각도와 트랙/표지판 치수를 먼저 확인하고 **합성 장면을 실제 조건에 보정**한다.
추정값과 실측값은 구분한다. 조명·반사·배경 무작위화는 관측한 실제 변화 범위부터 설정한다.

- 수집 세션마다 `session_id`, 촬영 장소·시간·조명 조건, 카메라 설정과 보정 버전을 기록한다.
- 원본 RGB 영상/프레임, 촬영 시각, 조작 명령·적용 시각을 함께 저장한다.
  원본 센서 시각을 사용할 수 없으면 기록 시각의 기준과 그 한계를 남긴다.
- 엔코더가 있으면 측정값을 별도 필드에 기록한다. **PWM 명령은 측정 속도가 아니다.**
- 차선 학습용 정답은 아래의 공통 동작 형식을 사용하고, 검출기는 9종 클래스의 bbox를 별도로 라벨링한다.
  같은 프레임을 두 작업에 활용할 수 있으나 정답 형식은 다르다.
- 표지판/신호가 없는 배경, 오인하기 쉬운 표시, 조명 반사와 먼 거리 사례도 수집한다.
  인접 프레임을 과도하게 중복 라벨링하기보다 다른 세션·조건을 확보한다.
- 실제 데이터를 **원본 촬영 세션 단위**로 train/validation/test에 먼저 분리하고 manifest를 고정한다.
  같은 원본 영상의 클립·복사본·증강본은 같은 분할에 둔다. 프레임 무작위 분리를 사용하지 않는다.
- 촬영 세션이 부족하면 독립 평가의 한계를 보고하고 추가 세션을 수집한다.
  세션 ID만 새로 부여해 같은 영상을 다른 분할로 취급하지 않는다.

수집·분할 도구는 프레임 수·세션 수·분할별 클래스 수, 빈 클래스와 중복 여부를 출력한다.
원본·라벨·manifest의 로컬 경로를 기록하고, 실제 데이터의 고정 분할을 세 가지 실험에서 공유한다.

### 차선 모델과 실차 동작의 공통 형식

현재 `train_policy.py`는 선속도(m/s)·각속도(rad/s)를 출력하지만, 기존 외부 `8_4.py`는 방향 각도를 사용한다.
새 수집기·학습기·실차 실행기는 동일한 동작 표현, 부호, 범위, 전처리와 메타데이터를 사용하도록 구현한다.

엔코더가 있으면 실제 측정으로 PWM→속도/회전 관계를 보정한다. 엔코더가 없다면 먼저
정규화 좌우 모터 명령 등 측정 없이 기록 가능한 공통 표현의 사용 가능성을 검토하고,
필요한 시뮬레이션/학습/실차 변환을 함께 구현·검증한다. 명령과 실제 운동을 구분한다.
기존 각도 라벨이나 PWM을 근거 없이 m/s 정답으로 변환하지 않는다.

이미 하단 자르기·YUV 변환·축소가 끝난 교재 수집 이미지는 원본 RGB 입력과 구분한다.
전처리를 두 번 적용하거나 RGB/BGR·상하 반전·출력 형식이 다른 가중치를 혼용하지 않는다.

## 2. 미세조정과 최소 실험 구성

합성·실제 데이터의 최적 비율을 미리 고정하지 않는다. 다음 세 가지를 최소 비교로 삼는다.

| 실험 | 학습 구성 | 확인할 점 |
|---|---|---|
| A | 합성 데이터만 학습 | 실제 조건으로 옮겼을 때의 성능 저하 |
| B | 실제 train만 학습 | 보유 실제 데이터로 얻는 기준 성능 |
| C | 합성 학습 → 같은 실제 train으로 미세조정 | 합성 사전학습이 실제 데이터 학습에 주는 효과 |

모델 구조·전처리·실제 분할·평가 조건을 맞추고 초기 가중치, 합성/실제 샘플 수, 학습 단계·반복 수·시간을 기록한다.
YOLO의 일반 사전학습 가중치는 실험 간 출발 조건을 맞춘다. 합성 데이터만 썼다는 표현과
일반 사전학습 가중치 사용 여부를 구분한다. 처음부터 여러 혼합 비율의 대규모 탐색은 하지 않는다.

`train_policy.py`에는 초기 체크포인트와 학습률 지정, 고정 실제 분할 읽기를 추가한다.
기존 차선 학습률 `1e-4` 대비 `1e-5`는 미세조정의 **첫 후보**이며 최적값으로 단정하지 않는다.
`train_detector.py`에는 학습률·optimizer·출력 실험 이름을 지정하고 기존 `.pt`를 불러와
새 데이터 학습을 시작하는 경로를 명확히 한다. 중단된 학습의 resume와 실제 데이터 미세조정을 구분한다.
Ultralytics에서 학습률을 직접 제어할 때는 optimizer를 명시하고 실제 적용 값을 로그에 기록한다.
[학습 설정 근거](https://docs.ultralytics.com/modes/train/)

**모델·학습률·검출 임계값은 실제 validation으로 선택하고, test는 설정을 고정한 뒤 최종 평가에 사용한다.**
현재 학습 스크립트의 자동 test 평가도 분리하여 반복 실험 중 test 결과를 선택에 사용하지 않게 한다.
test에는 학습·증강·임계값 탐색을 적용하지 않는다.
[데이터 누출 방지 원칙](https://scikit-learn.org/stable/common_pitfalls.html)

학습된 ONNX와 같은 이름의 JSON을 함께 내보내고 다음을 보존한다.

- 전처리·클래스 순서·출력 의미·단위·정규화 범위와 학습 설정.
- 초기 체크포인트 식별값, 원본 합성 학습 시드와 후속 실제 학습 세션의 출처.
- 고정 분할 manifest 식별값과 각 분할의 세션/프레임 수.

미세조정 후에도 합성 사전학습에 사용한 시드 이력을 유지하여 기존 배치 평가의 중복 시드 차단이 작동하게 한다.
오프라인 차선 오차·검출 성능과 실제 폐루프 주행/미션 성공률은 별도로 보고한다.

## 3. 실차 추론과 모터 제어 분리

현재 `run_sim.py`와 외부 `8_4.py`의 동기 실행 흐름을 실차용 비동기 실행기로 그대로 간주하지 않는다.
실차 실행기는 다음 구조로 구현한다. ROS 2 등 새 프레임워크 도입은 필수 조건이 아니다.

- 카메라는 촬영 시각·프레임 ID와 함께 **최신 프레임 한 개**를 제공한다. 오래된 대기 프레임은 버린다.
- 인식 작업은 최신 영상에서 정책/검출을 수행하고, 결과에 원본 촬영 시각과 처리 완료 시각을 붙인다.
- 모터 명령은 별도 주기에서 갱신한다. 느린 검출 추론이나 영상 저장이 모터 갱신을 막지 않게 한다.
- 결과 유효기간은 추론 완료 시각뿐 아니라 **원본 촬영 시각**을 기준으로 검사한다.
  오래된 영상으로 얻은 새 결과를 최신 관측으로 취급하지 않는다.
- 유효한 새 명령이 없거나 인식 프로세스가 멈추면 정지한다. 종료·예외·사용자 정지도 모터 정지를 수행한다.
- 시간 계산은 단조 증가 시계를 사용한다. 제어 주기·만료 시간·속도 상한은 설정하고 실측 근거를 남긴다.
- 추론 정지·느린 카메라·예외를 주입한 가짜 모터 테스트로 만료 정지를 확인한 뒤 실제 모터를 연결한다.

소프트웨어 주기 분리는 일반 Linux/Python에서 엄격한 실시간 보장을 뜻하지 않는다.
실제 주기와 지연 분포를 측정하고 제동 거리·주행 속도와 함께 판단한다.

### 엔코더가 없는 차량

기존 `MissionDriver`는 실제 바퀴 속도 입력을 요구한다. 엔코더가 없는 차량에서 목표 PWM을
측정 바퀴 속도로 넣어 기존 거리·회전·정지 판정을 통과시키지 않는다.
먼저 차선 주행·시각 검출·분홍선/횡단보도 관측을 검증하고, 시각 기반 접근·회전 판단과
중복 방지 등 필요한 대체 경로를 분리 구현한다. 관측이 불충분하면 정지/미검증으로 남긴다.
정지 명령을 준 시간과 실제 정지 확인을 구분하고, 외부 관측/영상 확인 없이 실제 정지 시간을 입증했다고 보고하지 않는다.
엔코더 장착 여부 때문에 데이터 도구·학습·오프라인 평가까지 중단하지는 않는다.

## 4. 라즈베리파이 지연과 주행 성능 측정

현재 ONNX 실행 경로를 먼저 측정한다. Pi에서 속도가 부족할 때 입력 크기·추론 빈도·CPU 스레드 경쟁을 조정하고,
필요하면 NCNN 등 ARM용 경로를 비교한다. NCNN 적용 시 기존 ONNX 어댑터를 대체하는 구현과 출력 일치 검사가 필요하다.
새 모델 계열로 바꾸는 작업은 필수 범위가 아니다.
[라즈베리파이 배포 참고](https://docs.ultralytics.com/guides/raspberry-pi/)

| 측정 항목 | 기록 기준 |
|---|---|
| 환경 | Pi 모델·OS·런타임/모델 버전·스레드·해상도·온도/스로틀링 확인 가능 여부 |
| 처리 단계 | 촬영/수신, 전처리, 차선 추론, 검출 추론, 판단, 모터 명령 적용 시각 |
| 전체 지연 | 촬영 기준→모터 명령 적용까지 p50/p95/최대. 촬영 시각이 없으면 수신 기준이라고 명시 |
| 제어 주기 | 실제 간격·목표 대비 지연, 기한 초과 횟수, 오래된 결과와 버린 프레임 수 |
| 출력 검증 | 원본/내보낸 모델의 동일 영상 출력 차이와 실제 검출·주행 품질 |
| 주행·미션 | 고정 시험별 시도 수·완주/실패·미션별 완료·중복·실행 위치 오류·중단 사유 |

준비 실행과 정상 실행 구간을 구분하고 짧은 추론 FPS만으로 전체 성능을 결론내리지 않는다.
실제 속도를 측정하지 못하면 PWM 설정값이라고 기록한다. 실제 이탈/완주 판정은 현장 영상 등
관측 근거를 남기고, 시뮬레이터의 정답 위치 기반 도로 여유를 실차 측정값처럼 사용하지 않는다.

## 구현 순서와 인계 기준

기존 [RTX 인계 절차](../RTX_HANDOFF_PROMPT.md)의 환경 점검·짧은 렌더링·교사 주행을 먼저 확인한다.
그다음 본 문서의 수집 계약 → 고정 분할 → 미세조정 → 모터 없는 실행기 검사 → Pi 측정 → 실차 시험 순으로 진행한다.
독립적으로 가능한 코드·도구 작업은 실제 장비나 데이터가 없는 동안에도 진행한다.
실측/주행이 필요한 단계는 실행 기기·관측 자료가 확보되었을 때 수행하고 미실행 상태를 표시한다.

후속 작업자는 아래 목록을 실제 근거와 함께 갱신한다. 필요한 도구 이름은 저장소 구조에 맞춰 정하되
아직 없는 도구의 실행 명령을 이미 동작하는 것처럼 문서화하지 않는다.
